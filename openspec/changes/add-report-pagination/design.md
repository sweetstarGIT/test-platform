## Context

`GET /api/reports` 当前按创建时间倒序返回固定 50 条 `Report` 记录，前端直接绑定数组，因此没有总数、页码或访问更早记录的能力。线上已超过该固定上限，报告列表需要同时在接口和单页前端实现分页。

## Goals / Non-Goals

**Goals:**

- 让用户能浏览所有报告，而不是只看到最新 50 条。
- 将每次返回量限定为固定、轻量的一页，并显示总记录数和可导航页码。
- 删除记录后保持当前页有效，避免出现空白页。

**Non-Goals:**

- 不改动报告 HTML 的详情加载性能；该问题独立处理。
- 不调整 `Report` 数据模型、历史报告文件或报告详情 URL。
- 不为包、任务或 CI 列表添加分页。

## Decisions

### 使用 offset/limit 分页，并以对象响应替代裸数组

接口接受 `page`（从 1 开始）和 `page_size`，默认每页 20 条，最大 100 条。响应返回 `items`、`total`、`page`、`page_size`、`total_pages`。

这是当前 SQLite 单表按时间倒序查询最简单且可预测的方案。游标分页更适合极大量、频繁写入的数据，但会增加前端导航与删除后的处理复杂度；当前报告规模不需要该复杂度。

### 前端维护独立的报告分页状态

保留 `reports` 仅存当前页项目，并新增总数、页码、页大小、总页数。仪表盘中的报告数改用总数；定时刷新只重载当前页，避免用户正在查看旧页时跳回第一页。

### 页码控件展示邻近页和边界页

展示首页、末页和当前页附近的有限页码，中间以省略号表示。这样在报告数增长时控件仍保持紧凑；上一页/下一页在边界禁用。

### 删除后重新拉取当前页并做越界修正

后端将过大页码钳制到最后一页，前端删除后以当前页重新请求。若删除导致当前页不存在，响应中的实际 `page` 会使前端自动回到有效页。

## Risks / Trade-offs

- [旧脚本把列表当数组解析] → 该接口是平台内部 UI 使用；响应变更会在路由文档与测试中明确，并同步前端。
- [页码在新增报告时发生变化] → 当前页按最新数据重载，用户仍保留在同一页编号；新报告只会出现在第一页。
- [总数查询增加一次 SQLite 查询] → `COUNT(*)` 在当前数据规模下开销可忽略，换来正确的总页数。
- [`page_size` 传入异常值] → FastAPI 参数约束将其限制在 1–100，阻止无效或过大的查询。

## Migration Plan

1. 部署新的后端与前端文件并重启平台服务。
2. 新页面立刻使用分页对象响应；现有报告详情链接不受影响。
3. 若需回滚，恢复路由和静态页面到前一版本即可；数据库没有迁移。

## Open Questions

无。默认每页 20 条，满足当前报告列表的浏览密度。
