## Context

报告列表已经采用服务端分页，但包、任务和 CI 仍使用未分页或固定上限的数组接口。前端将这些数组既用于列表，又用于仪表盘和 CI 状态卡；直接只保留当前页会使总数与状态统计失真。任务页面还会把同一 `batch_id` 的子任务合并显示，因此分页对象仍以任务记录为单位，同时保留当前页内的原有分组展示。

`/api/ci/jobs` 已写入开发侧对接文档，包和任务接口也可能被本地脚本调用。因此已有未带分页参数的请求必须维持既有数组结构和数量限制。

## Goals / Non-Goals

**Goals:**

- 让包、任务和 CI 页面可按页浏览完整历史记录，并显示正确的全量总数。
- 保留原有无分页参数的 API 响应，避免破坏 CI 查询和已有脚本。
- 让任务仪表盘与 CI 状态卡使用服务端全量统计。
- 停止测试报告的周期性刷新，消除页面浏览中的加载闪烁。

**Non-Goals:**

- 不修改数据库模型、报告 HTML、文件上传/下载或 CI 回调格式。
- 不对设备管理、项目介绍或报告详情页增加分页。
- 不改变批量任务的创建、取消和删除行为；任务页仅按其子任务记录分页，当前页内继续沿用批量分组展示。

## Decisions

### 查询参数触发分页对象，保留无参数数组契约

`page` 或 `page_size` 任一参数存在时，三个列表接口返回 `{items, total, page, page_size, total_pages}`；任务和 CI 额外返回全量 `status_counts`。参数未出现时，接口返回现有数组，保留任务 50 条、CI 100 条和包全量的旧行为。

这样新前端可统一使用轻量分页，外部开发平台仍可继续读取其原有的 CI 数组结果。替代方案是无条件升级所有接口响应，但这会破坏已给开发的 `GET /api/ci/jobs` 对接。

### 以稳定时间和主键倒序分页，并将越界页钳制到最后一页

各列表按 `created_at DESC, id DESC` 查询，以避免同一时间创建的数据出现跨页不稳定排序。默认页大小为 20，最大 100；空列表仍返回第 1 页、总页数 1。页码超过总页数时返回最后有效页，删除最后一页记录后前端无需额外分支即可恢复可浏览状态。

### 统计随分页响应一起返回

包只需要 `total`。任务和 CI 分别通过按状态聚合的 `status_counts` 返回所有记录的状态数量，前端不再以当前页数组过滤来计算“运行中”“已通过”等卡片。相比单独再请求统计接口，这减少了轮询时的请求数，也确保列表与指标使用同一数据库读取时点。

### 前端每类列表维护独立分页状态，报告不参加轮询

包、任务、CI 和报告各自保存当前页、页大小、总数和总页数。共享页码生成与范围文案逻辑，避免四套不一致的交互。任务、CI 与设备状态继续每 5 秒刷新当前页以反映运行变化；包只在上传/删除/手动相关操作后刷新；报告只在初次加载、翻页或删除后刷新。

## Risks / Trade-offs

- [未更新的调用方把带 query 参数的响应当数组] → 只由新版前端传递分页参数；无参数请求保持数组契约，并在路由文档中标明两种响应。
- [任务批次刚好跨页] → 分页计数以子任务为单位，当前页仍按 `batch_id` 合并展示；每页导航和总数明确指向任务记录，避免隐藏历史任务。
- [新增记录使用户所在页内容变化] → 任务和 CI 的定时刷新保留当前页码而非跳回第一页；报告不自动刷新，避免浏览干扰。
- [状态统计增加查询] → 使用轻量的 SQL `GROUP BY`；当前 SQLite 数据量适合该方式，并避免前端下载全量记录。

## Migration Plan

1. 部署后端和静态页面并重启平台服务。
2. 新前端立即通过分页参数调用三类接口；旧的无参数 CI 查询保持可用。
3. 如需回滚，恢复本次路由与静态页改动即可；不涉及数据库迁移或运行数据变更。
